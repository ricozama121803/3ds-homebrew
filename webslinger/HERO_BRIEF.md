# Web Slinger: hero model and animation brief

> **HISTORICAL.** This was the brief for the first refinement pass, written for the old rigid-parts model. The hero is now one continuous skinned mesh with mocap-driven locomotion; see `HERO_WORK.md` (current status) for how it works now. The 3DS limits and verification steps below still apply.

Goal: make the hero look less toy-like (better model, better suit texture) and make his walk / run animation look realistic.
Nothing here has been run on a real 3DS by the previous author, so keep the performance limits below.

## How the hero is built today

- 8 part types: torso, head, upper arm, forearm, hand, thigh, shin, foot. Left limbs only; the right side is mirrored in `hero_part()` (`mirror` flag). So the model must stay left/right symmetric.
- Each part is a separate rigid mesh with its origin at the joint, built by lofting ellipse rings (`PARTS` in `build_hero.py`). Parts are named `hero_<part>` in `hero.blend`.
- Blender conventions: Z up, hero faces -Y, hero's LEFT is +X.
- All parts share one 256x256 painted atlas (`hero_atlas.png`, generated by `build_hero.py`).
- `draw_hero()` poses the parts every frame: it computes hand and foot targets, solves two-bone IK for knees and elbows (`ik()`), smooths everything with critically-damped springs (`spring3`, `spring1`, struct `Anim`), then calls `hero_part()` per part. `SC = 1.38` scales the whole hero.
- Run cycle: `p->phase` advances with speed; foot path is a hand-tuned stance / swing curve, arms swing as sines. Wall run reuses the same cycle with the wall as the floor.

## Why it reads as a toy

- Rigid parts: joints show seams and bend like a doll.
- Roughly 1,700 triangles, simple lofted tubes, a flat painted texture.
- Proportions and silhouette are simplified.
- The run cycle is a sine-and-curve approximation: no real contact / passing phases, no pelvis motion, no ankle roll.

## Hard limits (3DS, do not exceed)

- Hero vertex buffer: `CAP_D_HERO` in `source/scene.h` is 7500 vertices = 2,500 triangles per frame. Current model is about 1,700. You may raise `CAP_D_HERO` modestly (the buffer is shared; check `CAP_DYN` and memory), but aim for 2,500-3,500 triangles total and tell the user if you raise it. The scene is drawn twice with the 3D slider on, so cost doubles.
- `hero_part()` keeps per-part scratch arrays of 700 vertices (`static V3 wp[700]`): a part with more than 700 vertices is silently skipped. Split the part or raise the array.
- One small texture only (keep the atlas 256x256 or smaller; the 3DS has very little texture memory, power-of-two sizes only).
- Vertex format is position, UV and a baked grey shade per vertex (`shadev`). There are no skinning weights or runtime bones on the GPU; any deformation must be done on the CPU in `draw_hero()` and stay cheap.
- If you rename parts or change joint origins, update the `HP_*` enum / `HERO_PARTS` export and every use in `draw_hero()`.

## Task A: the model

1. Look first. Run `make hero`, then `assets/hero/render_hero.py` for turnaround renders (see the script for usage), and `host/preview.sh` for how it looks in game. Study the current look before changing anything.
2. Improve the model within the limits above:
   - More anatomical proportions and silhouette: smaller head relative to the body, longer legs, a proper neck and trapezius slope, narrower waist, defined shoulders, calves and forearms.
   - Overlapping or capped joint geometry at shoulder, elbow, hip, knee and ankle so seams do not show when bent (for example a sphere cap on each joint, or ring profiles that overlap the neighbouring part).
   - Better hands and feet (separated thumb, a real shoe shape).
   - A better suit texture: panel lines, seams, web pattern, subtle muscle shading and ambient-occlusion style darkening painted into the atlas. Keep it readable at about 100 pixels tall on a 400x240 screen.
3. Keep it left/right symmetric and keep the character recognisable as the same red-and-blue web-slinger.
4. Hand-editing is also fine: `hero.blend` opens in Blender; `export_hero.py` re-exports it. But keep `build_hero.py` able to regenerate whatever you make, or say clearly that the `.blend` is now the source of truth.

## Task B: walk and run animation

Work in `draw_hero()` in `source/scene.c` (the `p->state == ST_GROUND` branch and the wall-run reuse of it). Targets:

- Real gait structure for run: contact, down, passing, up (two flight phases at sprint). Walk when slow, run when fast, with a smooth blend between them. Today there is only the run curve scaled by `amp`.
- Stride length and cadence scale with speed; feet do not slide on the ground (planted foot moves backward at exactly ground speed during stance).
- Pelvis: vertical bounce (lowest at contact/down, highest in flight), side-to-side shift over the planted foot, and rotation about the vertical axis.
- Spine and shoulders: shoulders counter-rotate against the hips, a small forward lean that grows with speed, and a little head stabilisation (the head stays level while the torso moves).
- Legs: heel strike or midfoot strike at contact, a bent knee absorbing the landing, ankle roll and toe-off at push-off, a heel recovery that kicks up behind, and a high knee drive at sprint.
- Arms: bent about 90 degrees, driving opposite to the legs, hands relaxed, elbows tracking slightly outward. Amplitude scales with speed.
- Transitions: standing to walking to running to stopping should look natural (a small lean back and a skid-in when stopping is fine), plus the existing landing crouch and roll must keep working.
- Keep the other modes working and looking at least as good as now: web swing (roped), wall run and climb, wingsuit, dive, tricks (front / back flips, rolls, corkscrew), jump crouch.
- The animation springs in `Anim` exist to blend poses. Fast cyclic motion needs stiff springs on the legs (see `runPose`), or sample the cycle directly without springs, otherwise feet lag and skate.

You are free to restructure `draw_hero()` (it is long), for example split the ground locomotion into its own function. Match the existing code style (tabs, terse C, comments on the why).
